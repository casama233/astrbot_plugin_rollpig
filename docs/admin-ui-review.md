# 管理后台 UI/UX 与 Analytics 重设计审计

## 现状问题

1. **展示感重于工作效率**：超大标题、玻璃拟态、漂浮光晕、较强阴影和卡片位移动画占用注意力，长期管理时容易疲劳。
2. **操作层级混杂**：数据观察、云同步、存储迁移和插件更新采用接近的视觉权重，危险操作不够独立。
3. **信息密度不稳定**：总览首屏偏松，图鉴和维护操作又偏挤；按钮组在中窄屏容易形成不规则换行。
4. **状态语义依赖文字**：成功、等待、错误和需重启状态主要靠文案辨认，扫描速度较慢。
5. **组件规范不统一**：圆角、阴影、输入框、卡片和弹窗的装饰强度偏高，焦点与忙碌状态不够系统。
6. **数据价值不足**：原总览能回答“目前有多少”，但缺少周期变化、回访、图鉴覆盖、长尾内容和玩法健康等管理判断。
7. **可访问性可加强**：动态弹窗、Toast、加载层和状态更新需要更完整的 ARIA 语义与焦点恢复。

## 改造方案

- 建立克制的中性色设计令牌，以粉色作为品牌强调色，状态色只用于成功、警告和危险。
- 将首屏改为紧凑工作台比例，降低标题高度、卡片阴影和动画幅度。
- 统一 6/8/12/16 像素圆角层级、按钮高度、焦点环、边框和阴影。
- 为同步、存储、更新建立操作卡语义，并用细色条区分类别。
- 为状态标签和反馈文案自动补充成功、等待、危险视觉语义。
- 为弹窗、Toast、加载层、状态区域补充 ARIA，并在弹窗关闭后恢复焦点。
- 新增独立的商业 Analytics 区域，展示双周期增长、7 日回访、28 日活动热力、图鉴覆盖分布、平台构成、上升猪猪和玩法运行健康。
- 深度分析采用渐进增强：原总览先加载；增强接口失败时只显示局部错误和重试，不影响图鉴、同步、存储或更新操作。
- 桌面优先，同时覆盖 1220、900、680、440 像素断点和减少动态效果偏好。

## Analytics 启动契约

- Analytics 只有在 `window.AstrBotPluginPage` 管理桥接可用后才会进入已就绪状态和读取聚合接口。
- 初始化采用 100ms 间隔、最多 8 秒的有界等待；重复脚本注入不会创建第二个轮询或重复绑定事件。
- 桥接长期不可用时只在深度分析区域显示局部错误和“重新连接”，普通总览、图鉴和管理写操作继续可用。
- AstrBot 会通过带认证的页面内容接口注入主 HTML，但浏览器子资源请求无法附带该授权头；因此企业主题、反馈增强和 Analytics 必须内联在主页面中。
- `/api/plugin/page/bridge-sdk.js` 是管理页唯一允许的外部脚本；不得重新引入相对 `pig-manager/*.js` 或主题 CSS 请求。
- 模块化 CSS/JS 文件继续作为维护来源，测试必须确认内联副本与源文件一致，并固定 Bridge → 反馈 → 企业增强 → Analytics → 主模块的执行顺序。

## 数据与隐私边界

- 新增 `GET analytics/insights`，只读取现有本地 SQLite 规范化表或 JSON 兼容数据。
- 接口只返回聚合数量、百分比、日期、小猪 ID／名称和平台命名空间摘要。
- 不返回用户 ID、群号、昵称、消息正文或原始聊天记录，也不把统计发送到外部服务。
- SQLite 后端直接聚合索引表；JSON 后端保留兼容计算路径。
- 不新增写入接口，不改变抽取、烧烤、吃群友、迁移、回滚、同步或安全更新流程。

## 非目标

- 不改变现有数据结构、写入权威、业务规则、确认流程或更新策略。
- 不引入前端框架、构建工具、遥测 SDK 或第三方分析服务。
- 不用装饰性假数据填充图表；没有数据时展示明确空状态。
- 不让深度分析接口成为其他管理功能的启动依赖。
