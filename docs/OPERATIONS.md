# 日常運維、版本升級與故障排查指南

本手冊專為插件管理員與專案維護者編寫，詳細涵蓋插件身分遷移、資料存儲架構、遠端資源同步、安全熱更新、資料備份以及常見故障排除方案。

> 本頁文檔完整對應 v3.12.4 的資料恢復、資源同步與安全更新規範。實際可安裝的穩定版本請一律以 GitHub 正式發佈的穩定 Release 頁面所附之 tag、ZIP 壓縮包與 SHA256SUMS 校驗檔為準；main 分支上的版本號變更並不代表 Release 已經發佈完成。

## 1. 版本規範與插件身分

### 升級至 v3.12.4 前的必讀檢查清單

目前插件 metadata 標記的版本為 v3.12.4，最低相容運行環境為 AstrBot `>=4.26.0`。唯有當自動化 Release workflow 針對通過 CI 測試的精確 main 提交正式建立出 v3.12.4 tag、ZIP 套件與 SHA256SUMS 時，才算是可供更新的正式版本。

執行正式更新前，請務必確認 GitHub 倉庫已發佈非草稿（Draft）、非預發佈（Pre-release）的目標 Release，且齊備對應的 tag、ZIP 與 SHA256SUMS；若 main CI 或 Release workflow 仍在執行中或意外失敗，切勿將分支代碼視為已發佈版本。透過插件管理工作台的安全更新功能取得穩定版後，請記得重載插件或重啟 AstrBot 以載入最新程式碼。

每次正式發版皆須同步更新 metadata、Changelog 與 Release Notes，完整通過 PR 檢查及 main CI 測試後，再交由 Release workflow 針對該精確提交產出全新的 tag、ZIP 與 SHA256SUMS。已發佈的穩定版 tag 與 ZIP 絕不覆寫，也請勿使用安全更新器強行安裝未經發版的任意分支。

更新插件本體程式與 `rollpig-source upgrade` 更新公共豬源服務屬於兩套獨立流程。升級插件版本並不代表公共豬源已同步切換 resource_version，且在任何情況下都不應擅自清空玩家的豬籍檔案或本地 EX 紀錄。

目前插件的註冊身分識別碼為 `astrbot_plugin_rollpig_plus`，而對應的 GitHub 專案倉庫名稱為 `casama233/astrbot_plugin_rollpig`。前者由插件 metadata 嚴格定義，兩者名稱不同屬於正常設計，並非版本衝突。

### 為什麼 v3.2.0 要更換插件身分識別碼？

由於歷史遺留原因，原版插件與本增強版過去曾可能共用相同的 `astrbot_plugin_rollpig` 識別碼。啟用獨立命名空間能徹底杜絕兩者共用配置檔、誤將原版資料當成增強版遷移，或是同一條抽豬指令同時觸發兩個插件並寫入同一個資料目錄的嚴重混亂。

## 2. 新安裝

若採手動安裝，存放目錄名稱必須與插件身分識別碼保持完全一致：

```bash
cd /AstrBot/data/plugins
git clone https://github.com/casama233/astrbot_plugin_rollpig astrbot_plugin_rollpig_plus
```

請重啟 AstrBot 服務，並確認管理後台正確顯示「今日小豬 · 增強版」。切勿將 v3.2.0+ 的程式碼強行塞入舊版程式或舊配置命名空間中啟動；內建的身分驗證機制會直接攔截並拒絕這種不安全的混用行為。

## 3. 從舊版增強版平滑升級至 v3.2.0+

### 觸發自動資料遷移的必要條件

系統必須能明確驗證舊目錄中的資料確實隸屬於本增強分支，例如偵測到 v3.1.4 專屬來源標記，或是符合增強版特有的 SQLite 結構與多檔案指紋。凡是無法確認歸屬的原版插件資料，系統一概不會自動搬運。

### 安全無損的遷移執行流程

```text
Copy → Verify → Atomic Commit
```

系統一律採取「先複製、不直接改寫舊資料」的保守策略；SQLite 資料庫會透過專屬安全備份機制處理，其餘圖檔與資源則以 SHA-256 等雜湊校驗核對。唯有在所有檔案全數複製並驗證無誤後才會切換啟用，且原始舊目錄仍會完整保留以備不時之需。配置檔方面僅會遷移 `_conf_schema.json` 支援的有效欄位，自動過濾未知或已廢棄的舊參數。

### 完成遷移後的驗收與收尾步驟

請逐一核對 `/今日小豬`、`/我的豬圈`、玩家統計數據、小豬圖鑑、本地自訂圖片以及 SQLite 資料庫的健康狀態。確認新版插件一切運作正常後，再手動前往後台停用舊版插件。

> 身分遷移流程不會擅自替管理員停用舊版插件。若新舊兩個插件同時處於啟用狀態，它們會同時監聽並註冊相同的群聊指令，進而導致在群組中出現重複回覆的狀況。

## 4. SQLite 資料庫運行與維護模型

### v3.0+ 的單一權威資料來源架構

規範化 SQLite 資料表扛起了核心運行時的資料權威：日常抽豬、圖鑑收藏、烤／吃狀態、AI 文案與身份映射等，一律以 SQL 事實表為準；SQLite 模式下的數據統計直接透過 SQL 聚合計算。舊版兼容 JSON 僅供遷移、匯出與回滾之用，系統不會持續雙寫作為最新副本。

### `storage_backend=auto`

官方推薦模式。全新安裝時會直接建立 SQLite；若偵測到可讀取的舊版 JSON，系統會先執行備份並匯入臨時資料庫，確認通過完整性、外鍵約束、規範化一致性及事實對帳檢查後，才會進行原子切換。

**唯獨初次遷移尚未正式提交就失敗時，系統才會保留原 JSON 繼續運行。**只要既有的 SQLite 無法開啟或驗證不通過，插件就會直接中止載入，絕不讓舊版或空白 JSON 趁虛接管。即便 DB 檔案消失，只要目錄內仍留有 SQL 權威記錄、無法核驗的狀態檔或 WAL／SHM 檔，系統同樣不會將其視為全新安裝。

`sqlite` 模式同樣受此恢復保護機制約束。`json` 僅適用於原生 JSON 安裝環境，或是已完成完整對帳與回滾的實例；既有的 JSON 仍會先以唯讀方式解析，一旦無法讀取便立即停止，絕不覆寫成預設值。單純將設定改成 json 並無法繞過 SQL 的安全保護。

當插件因異常停止載入時，本插件的管理面板也將無法開啟；請改為查閱 AstrBot 載入日誌與 [SQLite 恢復保護](SQLITE-RECOVERY.md) 進行排查。本版本未提供唯讀恢復工作台。

### SQLite 運行參數

底層啟用 WAL、`foreign_keys=ON` 與 `synchronous=NORMAL`，寫入鎖定等待時間受 `storage_busy_timeout_ms` 參數控制，預設為 5000 ms。具體有效數值範圍請參閱 [配置參考](CONFIGURATION.md)。

## 5. 資料與目錄結構

實際的資料根目錄位置取決於 `StarTools.get_data_dir("astrbot_plugin_rollpig_plus")`，系統不預設固定絕對路徑。完整的資料目錄內不僅包含主資料庫：

- `rollpig.db`、WAL／SHM 附屬檔、SQL 權威記錄與相關恢復材料。
- 圖鑑與歷史兼容資料、`local_overrides.json`、`deleted_pigs.json`。
- `images/` 本地小豬圖片、自訂本地 EX 資訊與其他玩法狀態檔。
- `cloud_resources/` 資源快取與同步狀態檔、PigHub 圖庫快取。

舊版 JSON 檔案沒有持續更新並不代表玩家資料遺失，但也切勿將它當成最新的災難恢復點。

## 6. 手動備份建議

在插件健康運行期間，可先從管理頁產出 JSON 匯出檔並核對時間戳與 SHA-256。但請注意，**JSON 匯出檔並不等同於整個資料目錄的完整備份**，它並未涵蓋所有本地圖片、EX 檔案或其他未受管檔案。

在進行主機搬遷、跨版本重大升級或任何檔案級操作前，請務必先停止所有可能寫入該資料目錄的 AstrBot 與插件程序，再備份整個目錄。開啟 WAL 模式時，切忌只單獨複製 rollpig.db 而遺漏周邊附屬材料。確認備份完整且核驗無誤後，方可展開人工操作。

切勿為了「重置」而逕行刪除疑似損毀的 DB、WAL、SHM 或權威記錄檔。插件停止載入時無法仰賴管理頁匯出功能；請先完整保留現場目錄，並在複製出來的副本上進行排查，詳細步驟請見 [恢復步驟](SQLITE-RECOVERY.md)。

## 7. 私人資源同步

系統預設啟用 AstrBot v1 專用資源源，全新安裝環境每隔 6 小時檢查一次更新；已有明確配置者則維持原設定不變。管理員可依需求關閉自動同步，或改用具備存取權限的兼容 HTTPS 私人源。

舊版 `pig.felislab.cc` 的精確 manifest 網址會自動遷移至 AstrBot 專用源；其餘自訂網址則維持原樣不予改寫。當私人源連線失敗時，系統不會擅自偷偷轉向官方公共鏈。

### 同步安全策略

同步機制僅接受 HTTPS 協定，並嚴格限制重定向次數、阻擋私網目的地，同時控管 manifest、資源包、單一檔案體積及圖片像素上限；必須等所有宣告的大小與 SHA-256 校驗全數通過，才會切換為 active 資源。若驗證失敗則沿用最近一次通過驗證的快取，毫無快取時才退回內置資源。

自 v3.12.3 起，公共 Vercel／GitHub 鏡像僅接納位於獨立批准清單內的完整快照。這些快照皆源自已完成審核並正式發布的 2026.09.05.1（涵蓋 164 隻小豬／820 級 EX）；系統遵循主源優先、私人源隔離原則，並拒絕降級至較舊快照。若批准表無法讀取，將繼續保留本地已驗證快取而不啟用新鏡像；一旦讀到撤回標記，便立即將對應的 mirror active 快取移出。詳見 [公共災備邊界](PUBLIC-MIRROR-FAIL-CLOSED.md)。

管理面板會明確區隔顯示「當前資源」的快取來源與「可用遠端」的來源鏈。快取的歷史來源不代表該來源目前仍獲准下載；若舊快取缺乏來源記錄，系統會誠實標示為未知，絕不依據當前設定反推猜測。公共鏡像的封鎖狀態亦會獨立列出。

手動觸發同步會在背景非同步執行，頁面本身不會自動輪詢進度。點擊右上角「刷新」可重新讀取最新狀態與圖鑑；提示「任務已啟動」僅代表請求已獲受理，最終成功與否請以刷新後讀取到的最新狀態為準。同步失敗時將保留現有資源，且關閉自動同步的提示訊息不會掩蓋實際發生的錯誤。

### 資源覆蓋優先級

底層基礎資料由有效的雲端／私人資源或內置資源提供；其上則以本地新增、編輯及自訂圖片為優先，而刪除屏蔽規則會在最後階段套用。因此，同步作業不會讓已被屏蔽的小豬 ID 死灰復燃；若需檢視或解除屏蔽，可前往管理頁的「本地資源」分頁操作。

Felis 官方直讀 overlay 屬獨立客戶端來源，不是公共鏡像再分發權。完整分層、manifest 和 403 說明見 [資源管理](RESOURCE-MANAGEMENT.md)。

## 8. PigHub 圖片導入與自建公共源投稿

管理員可於管理頁直接從 PigHub 挑選小豬圖片，並補齊名稱、描述與互動文案；圖片下載過程受 `resource_max_file_size_mb`、來源安全規則、圖片格式驗證及標準化規格限制。所有本地上傳的圖片皆妥善保存於插件資料目錄中，不會更動倉庫內的內置圖片。

欲提交投稿至公共源必須經過明確確認，並附上符合 rights-v3 規範的權利資料；實際送出的僅包含小豬資料、圖片與相關 EX 資訊，絕不會夾帶群友個資、群組資訊或聊天原文。請留意，能夠下載或在本地端使用，並不等同於擁有再次公開分發的權利。

維護者必須持有伺服器端的 `public_source_admin.token` 才具備審核權限。依據 `rollpig-public-source-service` 的 rights-aware 審核流程，**審核通過並不等於正式發布**：無論是 `publication_status=not_published`、空值的 resource_version，或是尚未切換 v1 指標，皆不算上線成功。正式發布還需經過來源驗證、候選快照檢查與原子切換程序；切勿因為舊版介面文案顯示「批准發布」就誤以為已經生效上線。

敏感的 Token 絕不應出現在前端程式碼、schema 定義或運行日誌之中。即使相關服務程式已合併進主幹，也不能用來替代生產環境的實際驗證，更不可擅自解除投稿 API 的安全隔離。

## 9. 管理面板安全更新

內建更新器僅會連接至 `casama233/astrbot_plugin_rollpig` 的穩定版 Release，絕不接受任意外部 URL、自訂開發分支或預發布（Pre-release）版本。

### 更新安全限制

更新包下載大小上限為 64 MiB，壓縮檔內檔案總數上限為 3000 個，解壓後總體積上限為 256 MiB；系統會嚴格攔截路徑穿越、符號連結以及異常壓縮比炸彈。只要 Release 附帶 SHA-256 校驗值便強制進行比對，若缺少校驗檔則會要求管理員額外確認。需注意，雜湊校驗本身並不等同於獨立數位簽章。

在執行檔案替換前，系統會自動備份現有程式碼；萬一更新失敗將嘗試自動回滾，並透過交易日誌協助中斷恢復。整個更新過程絕不會覆蓋玩家的歷史紀錄、本地圖片、玩法資料或設定檔。

### 更新完成後，為什麼版本號沒有立刻改變？

更新包安裝完畢後並不會自動重啟 AstrBot。這會導致磁碟上的已安裝版本與目前記憶體中仍在運行的載入版本暫時不一致；請在確認更新結果無誤後，手動執行重載或重啟。在尚未成功完成更新檢查前，切勿據此認定目前「已是最新」。

工作台會以「已安裝」明確標示磁碟上的實際版本，並清楚區分尚未檢查、更新操作失敗、已成功檢查及等待重載等狀態。唯有在成功檢查並取得完整 Release 資訊後，畫面才會顯示最新版本結論與 SHA-256 狀態；若檢查失敗，則保留上次的檢查結果、發行說明與成功時間，同時暫時停用安裝按鈕，必須重新檢查成功後方可繼續操作。處於已安裝但待重載狀態時，系統不會重複提供同一版本的更新。

## 10. AI 烤豬文案

此功能以 `enable_ai_roast_copy=false` 作為預設值。啟用後將調用當前會話模型生成專屬文案；生成超時時間受 `ai_generation_timeout_seconds` 控制，一旦模型不可用、發生報錯或超時，便會無縫回退至本地內置文案。同一隻小豬每天最多僅會嘗試生成一次，成功產出的文案將保留七個自然日的快取窗口供群友復用，避免因多人同時烤同一隻豬而重複消耗額度。

AI 文案生成失敗絕不會波及或導致 `/今日烤豬` 整體功能失效。

## 11. 常見故障排查

### 問題：啟動時跳出插件命名空間錯誤提示

請檢查手動 clone 的資料夾名稱是否仍舊沿用 `astrbot_plugin_rollpig`。自 v3.2.0+ 起應改用 `astrbot_plugin_rollpig_plus` 等獨立身份目錄，切勿試圖透過直接覆蓋舊目錄來繞過版本遷移程序。

### 問題：輸入一個指令卻收到兩次重複回覆

請檢查原版或舊版增強版插件是否仍處於啟用狀態，與現行增強版同時運行；身份遷移機制並不會自動幫您停用舊插件。

### 問題：每日抽豬重置時間不準確

請檢查 `timezone` 設定項。`local` 預設採用 AstrBot 主機的系統時區，若有跨時區部署需求，可明確填入 `Asia/Hong_Kong` 等標準 IANA 時區名稱；修改完成後請記得重載插件使設定生效。

### 問題：公共資源庫同步失敗

請先檢視同步狀態與運行日誌，確認 HTTPS 網址、DNS 解析與 TLS 憑證是否正常，確實有代理需求時才開啟 `resource_use_system_proxy`。切記不要先行刪除 active 快取，也不要把已被封鎖的公共鏡像當作可用備援。

### 問題：開啟系統代理後，資源同步反而卡住不動

系統預設不信任環境變數中的系統代理，藉此避免失效的 HTTP_PROXY 或 HTTPS_PROXY 拖垮連線。若伺服器本身能夠直連外部網路，請保持此選項關閉。

### 問題：SQLite 狀態顯示不健康或發生回退

請先釐清目前是「初次遷移尚未提交，仍沿用原 JSON」還是「既有 SQL 資料庫需要修復」。若屬於後者，本維護分支會直接停止載入插件，導致工作台無法開啟；此時請查閱 AstrBot 載入日誌，在停機狀態下完整備份資料目錄，並於副本上核驗資料庫或備份檔，確認修復無誤後再還原並重載。

切勿透過直接切換 `storage_backend=json`、刪除 DB 或移除權威記錄來強行繞過安全檢查。唯有在 SQL 狀態健康時，才能從管理頁先行匯出、對帳並執行明確回滾；請留意 JSON 匯出檔的時間點可能早於玩家最新進度。詳細處理流程見 [SQLite 恢復保護](SQLITE-RECOVERY.md)。

### 問題：管理頁的深度 Analytics 數據遲遲沒有載入

深度分析模組採用按需載入設計，不會阻擋核心總覽、圖鑑、資源同步、SQLite 狀態及安全更新等主要功能。請先確認是否已手動點擊載入入口；若是剛完成版本升級，建議重新進入插件管理頁或強制刷新 AstrBot 後台，以免殘留的舊版前端快取干擾渲染。

### 問題：聊天圖片發送超時後，群裡出現重複訊息

系統將圖片發送超時視為「投遞狀態不確定」，因此不會在超時當下立即補發另一份 fallback 訊息。若此現象可穩定重現，請協助記錄 AstrBot 版本號、通訊適配器類型、群聊或私聊環境、發生時間戳與完整日誌；切勿單憑 timeout 報錯就斷定訊息未送達。
