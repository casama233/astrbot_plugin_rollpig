# 小豬資源管理與維護指南

本篇指南適用於 v3.6.3 版本，專為需要打理本地圖鑑、維護 AstrBot／私人豬源，或負責公共源投稿的插件管理員編寫。

## 1. 資源分層架構模型

最終圖鑑並不是靠單一 `pig.json` 一股腦硬蓋過去，而是像疊積木一樣按層合併出來的：

1. **基礎層**：優先讀取順利同步下來的 AstrBot 專用源或私人源；萬一遠端連不上，就會自動退回使用插件自帶的內置小豬庫。
2. **本地覆蓋層**：你在管理面板裡手動新建的小豬記錄，或是針對基礎記錄修改過的名字、介紹、文案與圖片。
3. **刪除屏蔽層**：被管理員親手送進黑名單的 ID，在所有層級中擁有最高決定權。

另有独立的 **Felis 直读 overlay**：默认开启的非商业客户端会直接读取
[Felis 官方资源仓库](https://github.com/Felis2026/rollpig-resources) 的 manifest，
只会缓存通过审计的 34 个基础 ID 到 `felis_resources/active`。它既不是本站的 CDN，也并非
公共 Manifest 镜像；具体的来源、协议、配置和校验细节请查阅
[`docs/FELIS-DIRECT-RESOURCES.md`](FELIS-DIRECT-RESOURCES.md)。关闭
`felis_direct_enabled` 后既有 Felis 缓存也不会并入图鉴。

| 操作 | 結果 |
| --- | --- |
| 新建一個基礎層裡還沒有的 ID | 標記顯示為「本地新增」 |
| 修改一個基礎層原本就有的 ID | 標記顯示為「覆蓋基礎源」 |
| 上傳自訂小豬圖片 | 自訂圖片的顯示優先級高於私人源與內置圖片 |
| 刪除這隻小豬 | 清除本地覆蓋內容與自訂圖片，並將該 ID 關進屏蔽清單 |
| 解除屏蔽 | 移除刪除標記（tombstone）；只要基礎層裡還有同 ID，小豬就會立刻回來 |

如果解除屏蔽時基礎層裡已經找不到這個 ID，操作雖然依然算成功，但得靠你重新新增記錄，這隻小豬才會再次現身。

## 2. 管理面板日常操作流

### 檢視本地改動記錄

依序點開「插件頁面 → 今日小豬 → 本地資源」：

- 「本地新增與覆蓋」清單裡收錄了所有本地的 override 項目。
- 每張小豬卡片都會清楚標明它是「本地新增」還是「覆蓋基礎源」。
- 有沒有套用本地圖片也會單獨列出來。
- 點一下「編輯」就能進入完整的修改流程。

### 把原圖抓下來精修

1. 在圖鑑或本地資源頁面中，打開任意一隻小豬的編輯視窗。
2. 點擊「下載原圖重修」按鈕。
3. 在你的電腦或手機上完成裁切、重繪或修圖。
4. 回到剛才的編輯視窗，選擇「本地上傳」把新圖換上去。
5. 按下保存後，圖片規格會自動統一轉換為 `512×512 PNG`。

下載拿到的是當下實際生效的那張圖：本地圖片最優先，其次是 AstrBot 或私人源的 EX／基礎圖片，最後才輪到內置資源。只要某個 ID 存在本地資料 override，遠端或內置的 EX 文案差分就絕對不會蓋掉你的本地心血。

### 解除屏蔽

1. 進入「本地資源 → 刪除屏蔽」分頁。
2. 仔細核對小豬的 ID、名稱以及基礎層狀態。
3. 點擊「取消屏蔽」並進行二次確認。
4. 面板隨即會自動刷新總覽、圖鑑、資源層與同步狀態。

## 3. AstrBot 專用源與私人 manifest 機制

插件在預設情況下會連向本專案維護的 AstrBot v1 專用源：

```text
https://curryudon.top/astrbot-rollpig/v1/manifest.json
```

預設官方源配備了一套固定的故障轉移接力鏈：

1. `curryudon.top` 生產主源（更新速度最快、優先級排第一）；
2. 部署在 Vercel 上的已驗證公開快照；
3. `casama233/rollpig-public-source-mirror` 的 GitHub Raw 快照（可透過配置手動關閉）；
4. 最近一次通過驗證的本地快取；連快取都沒有時，才會退回使用插件內置資源。

唯有上一層發生連線超時、HTTP 異常、協議不符或完整性校驗失敗時，系統才會往下層切換。若備用鏡像的版本低於本地數字版 `resource_version`，系統會直接拒絕自動降級。

### 輕量安裝包與首次自動同步

GitHub Release／AstrBot Marketplace 安裝包只攜帶 **22 隻 bootstrap 小豬**、必要圖片、字體與運行代碼；完整作者資源仍保留在源碼倉庫並用於公共源建構與內容回歸測試，不會因安裝包瘦身而刪除。

全新安裝且尚未擁有任何已同步 `resource_version` 時，系統會在約 **3–10 秒**的隨機延遲後發起首次背景同步，優先從生產主源拉取完整公共圖鑑；若主源連不上，則會依序嘗試 Vercel 與可選的 GitHub 鏡像。萬一所有遠端來源全數失聯，內建的 22 隻 bootstrap 小豬依然能離線撐起基本玩法，後續的背景檢查也會按照設定週期持續重試。

這個瘦身只作用於發佈時的 staging 副本，不改動倉庫中的完整 `resource/pig.json`、作者 EX 文案或公共源生成輸入。

你也可以把 `resource_manifest_url` 換成自己有權限存取的 HTTPS 私人 manifest。這屬於明確的運維自訂行為；一旦指定了私人 URL，插件就只會認準這個來源同步，絕不會在同步失敗時偷偷切回官方公共源。

最小配置示例：

```json
{
  "resource_version": "2026.08.14-1",
  "pig_json": {
    "path": "pig.json",
    "size": 1234,
    "sha256": "64位小寫十六進制SHA256"
  },
  "images": [
    {
      "filename": "pig.png",
      "path": "images/pig.png",
      "size": 5678,
      "sha256": "64位小寫十六進制SHA256"
    }
  ]
}
```

對應 `pig.json`：

```json
[
  {
    "id": "pig",
    "name": "小豬",
    "description": "普通但可靠",
    "analysis": "今天適合把簡單的事情做好。"
  }
]
```


### 可選的 EX Lv. 差分機制

Resource Protocol v1 支援選配擴充 `pig_ex_variants.json` 與 `ex_variants/`。manifest 也會相應多出 `ex_variants` 檔案 metadata 以及 `variant_images` 陣列；沒有帶這些欄位的舊版 v1 或私人來源依然可以正常運作。

EX Lv.1–5 能夠分別覆蓋圖片、描述或整套文案，沒寫出來的欄位則會自動沿用較低等級的設定。要注意的是，差分不能拿來改動 ID、名稱或核心玩法規則。完整格式與顯示邏輯請見 [`EX-VARIANTS.md`](EX-VARIANTS.md)。

差分 JSON 與圖片會跟著基礎資源一起接受檔案大小、SHA-256、圖片解碼、整包容量預算與 staging 階段的嚴格校驗；只要有任何一項差分校驗沒過，active 資源就不會進行切換。

### 基本必要條件

- manifest 必須是 HTTPS URL。
- `resource_version` 絕對不能留空；只要內容有變動就必須同步更新。
- `pig_json` 以及每一張圖片都必須明確宣告 `size` 與 SHA-256。
- `pig.json` 裡列出的每一個 ID，都必須找得到對應的同名圖片。
- ID 命名僅限使用小寫英文字母、數字、`-` 與 `_`，長度限制為 1–64。
- 圖片格式只接受 PNG、JPG、JPEG、WEBP 或 GIF 副檔名。
- 基礎 manifest 最多可放 500 張圖片；可選的 EX 差分最多支援 1000 張圖片，且基礎加差分的總容量依然不能超過 128 MiB 的整包上限。
- 單一檔案的大小上限由 `resource_max_file_size_mb` 負責把關。

### 實戰部署建議

- 請為 manifest 與資源檔選用穩定的 HTTPS 靜態託管服務。
- 記得保留舊版本檔案，萬一發現新內容有問題才能隨時回退。
- 建議先在測試實例上跑通手動同步，確認無誤後再開啟自動同步。
- 千萬別拿需要 Cookie、登入驗證或特定客戶端 User-Agent 才能存取的網址當作公共 manifest。

## 4. 為什麼舊版雲端來源會頻頻失敗

舊版預填的 `https://pig.felislab.cc/resources/rollpig/manifest.json` 屬於 `nonebot-plugin-rollpig-plus` 的受限官方源。服務端會對本 AstrBot 插件回傳 HTTP 403，並拒絕未授權客戶端。

這並不是 manifest 解析異常、圖片格式不符，或是 SQLite 資料庫故障。從 v3.4.0+ 開始的運作邏輯如下：

- 全新安裝時會預設啟用 AstrBot v1 專屬資源庫，並將自動檢查更新的週期預設調整為每 6 小時一次。
- 既有的舊版 nonebot 來源網址會被精準無痛遷移至新源；而你自行設定的私人來源網址則會原封不動保留，不會被覆蓋。
- 全新的資源庫端點會強制驗證 `X-RollPig-Client`、`X-RollPig-Protocol` 以及帶有 AstrBot 版本號的 User-Agent 標頭。
- 一般網頁瀏覽器、格式錯誤的客戶端或舊版 nonebot 請求都會直接收到 HTTP 403 拒絕回應，唯有正統的 AstrBot v1 客戶端才能順利拉取圖鑑資源。
- 當遠端連線失敗時，系統會繼續沿用現有的本地快取；若連快取都不存在，則會安全降級回內置基礎圖鑑，並完整保留你的所有本地自訂修改。

通訊協議標頭本身可以被開源客戶端模擬，其設計初衷是為了過濾誤用與不相容的舊版請求，並不等同於嚴格的密碼學身分認證。若你架設了封閉私人源，請務必額外配置每實例專屬 Token 或 mTLS 憑證。關於來源伺服器的建構、部署與容錯回退細節，請參閱 [`RESOURCE-SOURCE-MAINTENANCE.md`](RESOURCE-SOURCE-MAINTENANCE.md)。

## 5. 自建 AstrBot 公共豬源投稿與審核機制

公共小豬資源庫與同步用的 manifest 皆由本專案團隊直接維護。雖然在新增或編輯視窗中仍可透過 PigHub 挑選圖片素材，但 PigHub 並不負責處理本插件的公開投稿或審核業務。

### 投稿包含的資料內容

會提交：

- 小豬的專屬 ID、名稱、詳細介紹以及全套互動文案。
- 經過標準化處理並轉換為 `512×512 PNG` 格式的當前生效小豬圖片。

系統絕對不會上傳以下隱私資料：

- 任何玩家個人資訊、群組名單或日常聊天紀錄。
- 本地 SQLite 資料庫檔案、JSON 備份檔或你的插件運行配置。

### 標準投稿作業流程

1. 投稿操作僅限從管理面板的「本地新增與覆蓋」清單中發起。
2. 管理員必須親自於瀏覽器介面上二次確認，才會送出公開投稿。
3. 插件會先在本地校驗欄位完整性、圖片編碼格式以及 10 MiB 的檔案大小上限，確認無誤後才發送至固定的自建官方 API。
4. 後端服務會自動擋下公共源已收錄的重複 ID、正在排隊審核中的重複 ID 或圖片，並針對單一來源實施每日投稿頻率限制。
5. 唯有在伺服器本機配置了維護專用 Token 的 AstrBot 管理面板，才會解鎖顯示審核工作區；該 Token 僅存於後端，絕不會外洩至前端瀏覽器。
6. 審核批准後，服務端會重新校驗整份圖鑑目錄的完整性、打包不可變的 release 版本、備份舊版目錄並以原子操作切換 `v1`；若遭拒絕，則僅留存審核紀錄而不予發佈。

顯示投稿成功僅代表資料已順利進入人工審核隊列，並不代表已經正式上架。為避免產生重複的髒資料，插件絕不會對這類帶有副作用的投稿請求進行自動重試。

## 6. 系統安全邊界與防護

- 所有後台管理寫入操作皆強制要求同源請求（Same-Origin）並須通過 CSRF token 驗證。
- 公共豬源的投稿與審核 API 端點均為寫死固定，管理員無法在前端面板隨意指定第三方上傳位址。
- 審核專用 Token 妥善存放於維護者插件資料目錄下的 `public_source_admin.token` 檔案中，與公開配置及前端靜態資源完全隔離。
- 所有遠端 API 回應與圖檔下載皆設有嚴格的體積上限；且公共服務僅放行攜帶正確 AstrBot Client／Protocol／版本標頭的合法請求。
- 進行私人源資源下載時，系統會主動攔截並拒絕指向區域網路（私網）、本機回環位址、系統保留網段及其他不安全目標的連線。
- 在整包資源的校驗程序完全通過之前，系統絕不會替換目前正在線上運作的 active 資源。
- 若資源同步中途失敗，系統會無縫保留舊版快取；若無可用快取，則安全回退至內置基礎圖鑑層。

## 7. 常見疑難排解（FAQ）

### 管理面板提示「來源不可用」怎麼辦？

舊版 nonebot 來源網址在升級至 v3.4.0+ 後會自動完成遷移。若你設定的自訂私人源依然顯示不可用，請依序排查 HTTPS 憑證、協議欄位格式、檔案大小限制、SHA-256 雜湊值以及遠端伺服器的回應狀態。

### 解除屏蔽後，圖鑑裡還是找不到那隻小豬？

這代表目前的基礎圖鑑層並未收錄該 ID 的小豬，且當初執行刪除時已一併清除了本地專屬紀錄與圖檔。請透過新增功能重新建立該小豬。

### 顯示投稿成功了，為什麼公共豬源裡沒有馬上出現？

公共豬源採取嚴格的人工審核機制；收到成功回應僅代表你的投稿已排入待審核隊列。必須等待維護者審核批准並打包發佈新版本後，各個實例才會在下一次自動同步時取得這隻新小豬。

### 私人源推送更新後，我之前在本地做的編輯會被洗掉嗎？

完全不會。私人源更新僅會替換最底層的基礎圖鑑，你設定的本地覆蓋（override）與屏蔽紀錄（tombstone）依然擁有最高優先權，不會受到影響。

### 萬一同步更新失敗，會不會把我的現有圖鑑全部清空？

請放心，絕對不會。只有當檔案下載、JSON 解析、體積檢查、SHA-256 校驗、圖片驗證與整體完整性測試全部過關後，系統才會執行原子切換。
