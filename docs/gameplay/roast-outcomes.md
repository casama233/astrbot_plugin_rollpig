# 🔥 烤群友 70 / 20 / 10：烤爐自有脾氣，開火全看天意

無論是一般 `/烤群友 @某人`、隨機烤群友，還是預約烤豬進入最終結算時，皆套用同一套核心判定機制：

這三項結果的機率權重即為 **70 / 20 / 10**。無論是 Roast Charge、發起預約或群友添柴，皆不會在背後更動這組基礎比例。

!!! info "添柴不是成功率 Buff"
    預約期間的多人添柴主要用於累積群聊熱度與觸發 Gameplay Event，**並不會提高最終的燒烤成功率**。當目標上線並觸發預約結算時，依然按照 70/20/10 的原始權重進行判定。

## 三種結算結果分別會帶來哪些影響？

### 🔥 70% 成功

- 目標將被正式記錄為本輪真正的 `victim`；
- 目標在本群的「今日被烤次數」將 +1；
- 生成專屬料理卡片；
- 該次紀錄將納入每日戰報的成功燒烤、最慘食材等相關數據統計。

一般燒烤成功**並不會將永久圖鑑中的小豬 ID 替換為熟食豬**。這僅屬於群聊互動事件與料理展示，不等同於重新抽取今日小豬。

### 💨 20% 逃脫

- 目標不會被計入一次實際被烤紀錄；
- 不會增加用於判定次日保護的「昨日被烤次數」；
- 依然會作為有效逃脫事件寫入 Gameplay Event 與每日戰報統計；
- 若本次一般群烤已扣除 Charge，即使目標成功逃脫，已消耗的點火能量也不會退還。

### 💥 10% 反噬

爐火調轉方向，開始檢視發起燒烤的主廚本人。

若主廚今日的小豬同樣符合可烹調條件：

- 本輪真正的 `victim` 將轉為發起者主廚；
- 主廚在本群的被烤次數將 +1；
- 料理卡片的內容將替換為主廚自己的今日小豬。

若主廚當下並無可烹調的今日小豬，反噬事件依然成立，但主廚得以「驚險逃過一劫」，本輪不會產生實際的 victim。

## 次日保護機制：昨日遭受重烤，今日獲發防火毯

當開啟 `enable_roast_protection=true` 時，系統會依據**同一群組**的歷史紀錄，檢視玩家昨日實際被烤熟的次數。

預設觸發門檻：

> **昨日於同一群組內實際被烤 ≥ 3 次 → 今日在常規玩法中獲得保護。**

此處計算的「實際被烤」，並非單純指「有人對你發起過幾次烤豬指令」。

| 昨天發生的事 | 算進保護計數？ |
| --- | --- |
| 對你群烤，70% 成功 | ✅ 算 |
| 對你群烤，但你 20% 逃脫 | ❌ 不算 |
| 別人想烤你，10% 反噬把主廚烤了 | ❌ 你不算；主廚算 |
| 預約最後成功烤到你 | ✅ 算 |
| 只是建立預約、還沒結算 | ❌ 不算 |

因此，保護機制的判定標準是**昨日真正被端上料理台的次數**，而非單純被點名的次數。

## 獲得今日保護後，哪些操作會被系統攔截？

所有常規燒烤流程皆會遵守保護規則，涵蓋範圍包括：

- `/烤群友 @某人`
- 隨機烤群友的目標池篩選
- 發起預約烤豬
- 一般吃群友的目標選定

後門強制模式雖能繞過「被烤保護」這層限制，但**無法無視基礎目標資格**。舉例來說，若目標身分為人類、已經是 `吃掉了`，或當日根本尚未抽取小豬，依然不符合常規可烹調目標的條件。

## Roast Charge 與結算結果屬於兩套獨立機制

Charge 系統決定的是：

> **「你目前是否具備足夠能量發起這一次常規點火？」**

70/20/10 權重決定的則是：

> **「爐火既已點燃，最終究竟是誰會遭遇不測？」**

因此，在一次常規群烤中，即便最終結果為目標逃脫或主廚反噬，Charge 依然會依照發起規則正常扣除。完整的能量運作邏輯請參閱 [Roast Charge 與烤箱補貨](roast-charge.md)。

## 預約烤豬的觸發與結算流程

當目標今日尚未抽取小豬，且有玩家對其發起預約時：

1. 首位發起預約的主廚需支付常規的 1 格 Charge；
2. 其餘群友參與添柴助威時，不會重複扣除 Charge；
3. 待目標稍後於**同一群組**內正式抽取並展示今日小豬時；
4. 該筆預約將即刻進行一次性觸發結算；
5. 仍按 70/20/10；
6. 結算完成時，系統不會因為「終於開烤」而向主廚二次收取 Charge。

更底層的一次性狀態流轉規則請參閱 [預約烤豬技術規則](../ROAST-RESERVATIONS.md)。

## 管理員可自訂哪些參數？

- `enable_roast_protection`：次日保護機制總開關
- `roast_protection_threshold`：昨日挨烤達幾次後今日開啟保護，預設 3
- `group_roast_max_charges`：一般群組內「烤豬」可累積的充能上限
- `group_roast_cooldown_hours`：單格充能的自然回復週期

**70/20/10 本身暫不開放手動配置。** 數值由核心 Roast policy 統一控管，防止各指令入口的規則各自為政。

## 料理卡文案是怎麼生出來的？

現在的料理卡早已告別單調的幾道固定菜色！插件自帶一份可離線運作的「豬言豬語」文案庫，將菜名與評語拆開隨機混搭；同一群組近期剛出現過的組合會暫時避開，大幅降低短時間內「撞菜」的尷尬。

官方 Resource Protocol v1 manifest 支援選配發布 `roast_copy` 文案包。當遠端同步成功時會優先採用雲端新詞；若遠端未提供、下載中斷或校驗未過，系統則無縫切回插件內置文案庫，完全不影響日常抽豬與烤豬體驗。

開啟 AI 料理文案功能後，每隻小豬每天依舊只會呼叫一次模型，但單次請求會一口氣產生最多 4 組不同候選文案，並匯入近七天的候選池輪替使用；舊版本留下的單條 AI 文案也能正常相容讀取。此外，AI 文案與本地文案共用同一套近期防重複機制。
