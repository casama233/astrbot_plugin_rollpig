# 預約烤豬

預約烤豬把「目標今天還沒抽豬」從一次失敗提示改成同群當日的異步埋伏玩法。它只作用於明確指定目標的普通 `/烤群友 @某人`；隨機烤群友和後門強制模式保持原行為。

## 建立與添柴

當 `enable_roast_reservation=true` 且目標今天尚未抽豬時：

1. 第一位使用 `/烤群友 @目標` 的有效玩家成為固定主廚。
2. 主廚必須先抽到自己今天可料理的小豬，並消耗一次原本的「發起者 + 群組」烤架冷卻。
3. 同一天、同一群、同一目標只存在一張待結算預約。
4. 後續其他群友可直接使用 `/添柴` 加入待結算預約；如果本群同時有多張預約，請使用 `/添柴 @目標` 指定。為相容舊玩法，再次 `/烤群友 @同一目標` 仍然會視為免費添柴。
5. 添柴者仍需先抽到自己今天可料理的小豬，但加入已有預約不消耗自己的 Roast Charge。
6. 主廚在建立預約時已經算作第一位參與者，因此不能再給自己添柴；同一參與者重複加入也不重複計數，插件會直接說明原因。
7. 參與人數包含主廚，預設上限 12，可由 `roast_reservation_max_participants` 在 2–20 之間調整。

`/添柴` 是正式由插件接管的指令。即使目前沒有預約、發起人重複添柴、使用者已經加入、烤箱已滿或需要指定多張預約中的目標，插件都會回覆明確規則提示，不會把這類已知業務拒絕交給聊天模型自由發揮。

建立預約仍尊重昨日過度被烤保護。後門口令不建立預約，也不會把尚未抽豬的目標強行變成可烤狀態。

## 何時觸發

預約以「自然日 + 群組 + 目標」隔離。目標本人在**同一群**正常使用 `/今日小豬` 並顯示自己的今日結果時，待結算預約才會觸發。

這意味著：

- 目標在其他群抽過豬，不會把本群埋伏結果投遞到錯誤群；
- 只讀 `/今日小豬 @某人` 不會替被查看者觸發預約；
- 目標之後回到預約群再次查看自己的今日小豬，仍可觸發當日尚未結算的埋伏；
- 預約不跨自然日繼承，舊狀態會按日期裁剪。

## 結算

建立預約時已經支付普通烤架冷卻，因此觸發時**不會再扣第二次冷卻**。結果沿用普通烤群友：

- 60%：成功，目標今日小豬上桌；
- 30%：目標逃脫；
- 10%：反噬固定主廚；如果主廚當時沒有可料理的小豬則幸免。

添柴人數目前是社交展示和事件資料，不直接增加成功率，避免多人堆到 100% 成功而破壞原本 60/30/10 的戲劇性。

## 一次性與投遞安全

預約會在任何結算訊息發送前先從 `pending` 原子標記為 `resolved`，並固定本次 outcome。這是刻意的「至多一次」語義：如果某個訊息適配器在已接受消息後回報超時，插件不會因自動重試而再次烤一次。

狀態保存在插件資料目錄的 `roast_reservations.json`，只保存短期玩法所需的日期、群、主廚、目標、參與者和結算狀態；小豬收藏、冷卻與被烤次數仍由現有 SQLite／JSON 權威資料管理。

## Gameplay Event

預約流程寫入共用 Gameplay Event v1：

- `roast_reservation_created`
- `roast_reservation_joined`
- `roast_reservation_triggered`
- 最終仍寫既有 `roast_success` / `roast_escape` / `roast_backlash`

因此現有豬圈日報的燒烤、逃脫、反噬和稱號統計能自然納入預約結算，不需要另外維護一套日報統計。

## 配置

| 配置 | 預設 | 說明 |
| --- | --- | --- |
| `enable_roast_reservation` | `true` | 允許明確指定未抽豬目標時建立／加入預約 |
| `roast_reservation_max_participants` | `12` | 每張預約最多參與人數，包含主廚，範圍 2–20 |
| `group_roast_cooldown_hours` | `8` | 第一位主廚建立預約時消耗原本的普通烤架冷卻；添柴不消耗 |
| `enable_roast_protection` | `true` | 預約建立同樣尊重昨日過度被烤保護 |
