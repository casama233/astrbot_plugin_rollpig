# RollPig 文案風格：先把規則講清楚，再讓小豬補一刀

這份規範約束所有**玩家會看見的文字**：聊天回覆、動態幫助、玩法提示、錯誤 fallback、豬圈日報、Wiki / README、永久豬籍 renderer，以及小豬 `description / analysis` 與 EX 文案。

目標不是讓每一句都變成段子，而是讓玩家即使只看到一條純文字，也能認出：**這是《今日小豬》的後廚，不是通用 Bot 的狀態機。**

---

## 1. 核心節奏

推薦順序：

1. **先講結果／規則**：第一眼知道發生什麼。
2. **再放進豬圈世界觀**：後廚、烤架、主廚、食材、柴火、豬籍、豬圈保安……
3. **最後有空再補一刀**：一句具體的小反轉，比三句抽象形容詞更有記憶點。

例如：

> 🪵 你的名字已經在柴火簿上了。再塞不加人頭，只會讓烤箱懷疑你有私情。

第一句交代「重複添柴不計數」，第二句才負責好笑。

---

## 2. 玩家拒絕：要明確，不要像後端狀態碼

### ✅ 推薦

> 🐷 一個人搬柴不叫補貨，叫加班。今天本群至少要有 2 位養過豬的群友。

> 🪵 你就是這口鍋的主廚，開局已經算 1 人。不能左手當主廚、右手再冒充群友——叫別人來 `/添柴`。

> 🍴 不能吃自己。後廚還沒窮到要做閉環供應鏈。

### ❌ 避免

> 條件不滿足。

> 當前狀態不允許此操作。

> 活躍玩家不足。

規則可以專業，**玩家不需要看見狀態機的口吻**。

---

## 3. 技術錯誤：真實原因永遠優先於笑點

技術故障不能只說「小豬暈了」「帳房先生死了」。必須讓管理員知道哪一層真的失敗。

### ✅ 推薦

> 🧯 菜做好了，但料理卡畫師把鍋掀了。**圖片生成失敗**，請稍後再試。

> 🧯 嘴已經張開，但豬圈帳本沒記住這一口。**吃群友狀態寫入失敗**，請稍後再試。

> 【我的豬圈】收藏還在，圖鑑畫師先罷工了。**圖片生成失敗**，請查看後台日誌。

結構是：**可辨識的錯誤原因 + 一句世界觀包裝 + 必要的下一步。**

---

## 4. 世界觀詞庫

優先使用具體、有畫面的詞：

- 玩家：`群友`、`主廚`、`食材`、`柴工`
- 遊戲空間：`豬圈`、`後廚`、`烤架`、`料理台`、`鍋`
- Roast Charge：`火`、`Charge`、`柴車`、`搬柴`、`添柴`
- `/添柴`：補貨輪次中代表補貨；`/添柴 @目標` 明確代表預約添柴。必須說清楚是哪一口鍋。
- 預約：`埋伏`、`蹲鍋`、`添柴`、`柴火簿`
- 保護：`豬圈保安`、`豬身安全險`
- 日報：`晚報`、`報紙`、`上榜`
- 圖鑑／收藏：`永久豬籍`、`豬籍檔案`、`入圈`、`返場`、`老豬留檔`、`翻豬牌`

不要為了世界觀故意藏掉精確名詞。第一次出現可以寫：

> 每人每群有 2 格 **Roast Charge（烤箱火）**。

---

## 5. 永久豬籍／圖鑑 renderer

圖鑑不是管理後台報表。它可以完整保留精確數字，但標籤應像玩家正在翻自己的收藏：

### ✅ 推薦

- `我的豬圈 · 豬籍檔案`
- `現役入圈 37/201`
- `老豬留檔 4`
- `最常返場 豬葛亮`
- `老豬籍 · EX Lv.3 · ×4`
- `還沒拱進你家`

### ❌ 避免

- `active unlocked`
- `historical retained`
- `unknown item`
- `locked`

**數字不變，口吻變。** 「歷史保留」是資料模型；「老豬留檔」是玩家看到的 copy。

卡片標籤還要考慮版面：短、能掃讀、不把笑話寫到溢出格子。

---

## 6. 小豬 `analysis`：禁止人格測評模板

一隻好豬通常有這個節奏：

**外觀／設定 → 具體行為 → 群聊或豬圈梗 → 最後補刀。**

### ✅ 推薦

機械豬：

> 群裡罵誰「人機」你都對號入座，因為你是真·機器——運算精準、從不摸魚，唯一的 bug 是偶爾忘了自己其實是隻豬。

大懶豬：

> 別人卷工作、卷學習，你只負責把被子卷到下巴——不是沒有上進心，是你的上進心也想躺會兒。

烤豬：

> 別的豬面對壓力會成長，你面對壓力會出餐——成熟是真的成熟，就是熟得有點物理。

### ❌ 避免

> 你性格隨和，追求舒適，不喜歡壓力。

> 你真誠又有魅力，值得被大家喜愛。

> 你是一位可靠、成熟、值得信賴的前輩。

把豬名換成任何星座、MBTI 或另一隻豬後仍然成立的句子，通常都太泛。

---

## 7. EX 文案：不是把「熟悉度 +1」寫五遍

EX 每級至少做到一項：放大原設定、延伸到新群聊場景、讓返場次數成為笑點，或在 Lv.5 做「完全體／常駐節目」式收束。

不要只寫：`熟悉度提升 / 關係升溫 / 最終形態`。能無痛套在 200 隻豬身上的內容不夠像 EX。

---

## 8. 動態幫助：準確性高於段子，但不能像 API 文件

每項最好是：**有性格的短標題 + 精確的一句規則。**

> **新豬保底｜豬圈不許一直敷衍你**  
> 老面孔連續返場時，未解鎖小豬的重抽機會會越攢越高。

> **群體補貨｜烤太猛就一起添柴**  
> 大家添柴達標後，今天活躍群友各恢復 1 格 Charge。

不能為梗把數字、權限、恢復時間、概率或條件藏起來。

---

## 9. Wiki / README：豬味和真實性同時是契約

玩家文檔要比 API 文件好讀，但**不能比程式慢一版**。

- 玩家入口只主推現在的 canonical command；compatibility alias 放到「相容」說明，不跟主命令並排搶戲。
- 功能改成 Charge 後，文檔不能再把 `group_roast_cooldown_hours` 寫成整個人的單一冷卻。
- 一個 command 有上下文路由（例如 `/添柴`）時，首頁、快速開始、玩法頁、COMMANDS、CONFIGURATION 必須用同一套判定順序。
- 技術文檔可以少講笑話；SQL、協議、權限、原子性、fail-closed 等條款優先精確。
- 版本化歷史證據不能被拿來當現在的操作手冊。

推薦結構：**一句人話摘要 → 精確規則／表格 → 一個具體例子 → 必要時最後補一刀。**

---

## 10. Mention 排版

群聊純文字提示中，`@` 對象單獨一行：

```text
@某位群友
🔥 你剛抽完豬，後廚埋伏立刻掀鍋！
主廚帶著 3 位添柴群友開始結算。
```

不要回到 `@某位群友 🔥 ...` 的整塊長訊息。

---

## 11. 繁簡體

`zh-TW` / `zh-CN` 應：

- key 集合一致；
- format placeholder 一致；
- 各自使用自然字形；
- 不能因共用替換把「后厨／後廚」串進同一句。

翻譯不是逐字轉換，梗可以微調，但玩法規則不能變。

---

## 12. PR Copy / Docs Review 清單

新增或修改玩家可見內容時至少確認：

- [ ] 第一眼能知道結果／拒絕原因嗎？
- [ ] 技術錯誤保留真正失敗層嗎？
- [ ] internal state 是否直接吐給玩家？
- [ ] 世界觀是否具體，而不是抽象形容詞？
- [ ] 梗有沒有遮住數字、權限、Charge、概率或下一步？
- [ ] Wiki / README / COMMANDS / CONFIGURATION 是否仍描述同一個功能？
- [ ] canonical command 有沒有被舊 compatibility alias 搶回主入口？
- [ ] 圖鑑／卡片 renderer 的文字是否也一起審查？
- [ ] `@` 長提示是否換行？
- [ ] `zh-TW` / `zh-CN` placeholder 是否一致？
- [ ] 小豬 analysis 換成任意星座仍成立嗎？如果成立，重寫。

最後標準不是「每句都好笑」，而是：

> **規則看得懂，世界觀接得住，偶爾還會被小豬補一刀。**
