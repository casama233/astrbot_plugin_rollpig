# 🧯 常見故障與疑難排解

动手排查前先分清：**究竟是触发了游戏规则限制，还是后台程序真的罢工了。**

## 发送 `/今日小豬` 今天却抽不到新猪

建议先从以下两个方向确认：

1. **昨天是否刚被群友吃掉。** 在默认设置下，被吃后的次日首抽有 20% 概率必出已解锁的重复猪；此时抽猪流程依然正常算作完成，并不会锁定到自然日结束。
2. **服务器与本地时区是否一致。** 每日刷新的重置时间以 `timezone` 为准，未必与你所在地的午夜零点同步。

若排除了上述规则因素，再去后台日志检查是否有 storage 存储、图片生成或资源加载相关的报错。

## 使用 `/今日小豬 @某人` 無法查看對方的猪

这项偷看功能需要管理员先在后台开放权限：

```text
at_view_pig = true
```

权限开启后，`/今日小豬 @某人` 仅用于查看对方当天已经抽出的结果；**绝不会帮对方代抽、解锁新图鉴，也不会触发任何群烤预约**。

如果管理员尚未开启 `at_view_pig`，请先联系群内管理员检查插件配置。

## `/烤群友 @某人` 指令无法使用

请按照以下顺序逐项排查：

- 当前是否处于群聊环境中（私聊无法开烤）；
- 后台配置的 `enable_roast` 与 `enable_group_roast` 开关是否均已打开；
- 你自己今天是否拥有处于可料理状态的小猪；
- 指定的目标是不是你自己（不能自己烤自己）；
- 目标当前是否为人类形态、已经被吃掉，或正处于其他不可料理的状态；
- 目标身上是否还挂着昨日被吃后的次日保护期；
- 你手头的 Roast Charge 料理次数是否已经耗尽。

若目标今天尚未抽猪，且本群已开启预约功能，明确指定 `/烤群友 @某人` 将会直接挂起一张群烤预约单，不会当场开火结算。

[完整群烤規則 →](../gameplay/roast-outcomes.md)

## 明明烤的是群友 A，為什麼出爐的料理卡卻是我？

普通群烤存在操作翻车的反噬风险，默认的翻车后果如下：

- 70% 成功
- 20% 逃脫
- 10% 反噬

一旦触发料理反噬，只要发起主厨自己当天的猪处于可料理状态，最终被架上烤架变成料理的就会是主厨本人。

## 發送 `/烤箱補貨` 卻提示我沒有資格

无论是发起补货还是参与支持，双方都必须是**今天在本群留下过 RollPig 活跃记录的玩家**。

此外，也可能是以下几种状况导致的：

- 本群今天的补货成功次数已经达到每日上限；
- 群里当前已经有一轮补货正在进行中；
- 管理员在配置中关闭了 `enable_oven_refill` 功能。

即使你自己的 Charge 已经蓄满，依然可以出手帮群友添柴支持；只是补货成功后，你的个人上限不会因此溢出。

## 發送 `/添柴` 卻沒有成功加人頭

`/添柴` 同时承担了「补货添柴」与「群烤预约」两种职能，常见的响应失败原因包括：

- 你今天还没有在本群参与过任何 RollPig 互动；
- 你自己今天没有可供料理的小猪；
- 你已经对同一轮补货或同一张预约单投过支持票了；
- 你本身就是该预约单的发起主厨或被预约的目标；
- 群内当前并没有正在进行的补货轮次，也没有待结算的预约单；
- 场上同时存在多张预约单，但你发送指令时没有指定具体的 `@目標`；
- 该张预约单的人数刚好凑满，或者已经进入开烤结算流程。

当补货正在进行时，直接裸发 `/添柴` 会优先计入补货添柴；如果想明确加入群烤预约，请使用 `/添柴 @目標`。

`/添煤`、`/加煤` 等早期写法目前仅作为补货兼容入口保留，建议日常直接使用 `/添柴`。

[完整 Charge 與添柴規則 →](../gameplay/roast-charge.md)

## 群聊日報為什麼沒有按時自動發送？

触发自动播报群聊日报，必须同时满足以下前提：

1. 全局 `daily_report_auto_send = true`；
2. 当前所在群聊已由 AstrBot 管理员在后台明确开启了自动日报推送。

可以先在群聊中发送以下指令自查：

<span class="pig-command">/豬圈日報狀態</span>

如果开启了 `daily_report_skip_empty_groups=true`，当天没有任何抽猪活跃记录的冷清群聊也会被自动跳过。

手动触发的 `/豬圈日報` 永远只做数据展示，不会触发可选的「今日祭品」结算。

## 同步圖鑑與圖片資源時出現 403

如果配置文件中仍然填写着旧版资源地址：

```text
https://pig.felislab.cc/resources/rollpig/manifest.json
```

请及时更换为当前的 AstrBot 专用资源源，或等待新版插件自动完成迁移。官方默认地址为：

```text
https://curryudon.top/astrbot-rollpig/v1/manifest.json
```

如果你使用的是自建私人资源源并遇到 403 报错，请重点检查自己的访问认证、请求 Header 或反向代理配置。

## 同步失敗的話，圖鑑裡的小豬會被清空嗎？

正常情况下不会。远端资源需要先通过完整校验才会切换过去；万一同步失败，系统会继续沿用旧缓存，如果没有缓存则会自动退回使用内置资源。

所以千万别因为一次同步失败，就急着删掉 `cloud_resources/` 或数据库。

## 投稿顯示成功，但在公共源裡卻找不到

投稿成功仅代表**已进入人工审核队列**，并不是立刻公开上线。等审核通过并打包出新版本后，其他实例也得等到下一次同步才会刷出来。

[創作者與投稿流程 →](../creators/index.md)

## 更新完之後，版本號或管理頁看起來都沒變

插件更新完毕后并不会自动重启 AstrBot。请先确认更新确实成功，然后再手动重启主程序或重载插件。

如果是旧版 overlay 升级残留下来的管理页，v3.8.1 及之后的版本会在启动时自动清理已知的旧 Plugin Page。

## SQLite 看起來好像出問題了，能直接把 `rollpig.db` 刪掉嗎？

强烈不建议直接删。请按以下步骤排查：

1. 先暂停持续写入操作；
2. 完整备份整个插件数据目录；
3. 查看具体的 storage 报错信息；
4. 根据实际情况决定是恢复、回退还是重新迁移数据。

[運維、備份與恢復 →](../OPERATIONS.md)

## 回報 Bug 的時候最好附上哪些資訊？

请至少提供以下信息：插件版本、AstrBot 版本、所用适配器、触发问题的指令、出现场景（群聊或私聊）、报错前后的完整日志，以及相关的配置项数值。

**切记不要贴出 Token、密钥或其他任何私密凭证。**
